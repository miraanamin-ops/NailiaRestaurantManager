# Naila (working name)

## What this is
An AI marketing assistant for independent single-site restaurants. The owner runs everything through WhatsApp: the AI drafts the work, the owner taps Approve, Edit or Skip, and nothing goes out unless it passes plain-code safety rules. The user is not a developer, so explain things simply and give exact click paths when you need something from them.

Right now it's being built to test alone with dummy data. No real customers, no live Google connection.

## Stack
Next.js (TypeScript) on Vercel, Supabase (database), GitHub, Claude API (Sonnet), Twilio WhatsApp sandbox (owner channel only), Resend (customer emails from our verified domain mail.dinerai.co.uk, EU region; React Email templates). All keys are Vercel environment variables, never in code.

## Built so far

21. Agent organisation, phase 4 (the GM): the GM (`agents/gm.md`) sits between the owner and the specialists. First, three loose ends: the Agent tests workflow runs only when started by hand; a plain-code price check (every £ amount in a Reputation, Visibility or Growth draft must be a menu price, a value in the offer's fields or the owner's own offers); Growth's send time is used (the gate holds an approved campaign as "scheduled" and the hourly job sends it when due; `024_gm.sql`). A Haiku router reads each owner message and picks one of: reviews, Visibility, one-off writing, Insights, Growth, a fact about the restaurant, a simple profile question, general chat, or "unclear". Fixed commands (APPROVE, SKIP, RUN..., UNDO etc.) stay in code and never reach it. A Sonnet composer writes the GM's words: the brief summary, one short card per item, alerts, replies to simple profile questions (checked by the checker before sending) and the 2-line Monday message; receipts and every number come from code. Rules in code: at most 5 brief cards, urgent first, then by send date, then oldest, the rest roll to tomorrow; at most one alert an hour (a second waits for the next hour) and none in quiet hours (they go when quiet hours end, released by the hourly job, and are dropped if dealt with first); skip offers three one-tap reasons (Wrong tone / Wrong offer / Not now), never a follow-up question; an unclear message gets one question with 2 or 3 buttons; a fact about the restaurant ("we close at 11 on Fridays now") becomes a confirm card with Approve / Edit / Skip that saves through the settings flow (UNDO-able); an "On it, back in a minute" line if a reply takes over 8 seconds, at most once, in the owner's language. Scheduled work's questions (Growth's Monday questions, Insights' missing till reports) arrive in the brief as cards answered in words, and the answer goes back to that agent; Growth's special ideas arrive as Draft-only cards with Like it / Skip. General chat and look-ups stay with today's assistant for now. Shadow (the default): the router runs on every message and a shadow brief on every brief, beside today's on /log (GM comparison, with times). Live (test mode only, once the checklist passes: owner name, language, quiet hours and at least one specialist live): the GM routes, composes the brief, the Monday message and alerts; today's code answers whenever it can't. 40 routing cases and 11 composer cases.
22. TEST_MODE split into separate switches (`src/lib/switches.ts`, pure and unit-tested), so an agent can run live for one restaurant without redirecting every customer's email. TEST_TOOLS: test commands, the test clock, RESET ONBOARDING, new sign-ups as demo restaurants, a test phone moving between demo restaurants; off unless set, and they only ever act on demo restaurants. GOOGLE_MODE: dummy (default) / simulated (reads live Google, posts nothing) / live; preview and development never write to live Google. TEST_MODE is deprecated: it only fills in a switch that isn't set, so TEST_MODE=true behaves exactly as before. Each cron run records its switches (`job_runs.switches`, `supabase/025_job_switches.sql`); /log (builder only) shows the switches now and marks runs where they changed; builder controls show each switch and, per agent, why one set to live runs in shadow; each agent mode or trust level change is named in its audit line. STATUS shows test tools and email redirect.
23. A job queue in Supabase instead of one long hourly run: the hourly job now only queues work (one job per restaurant per task: review check, held GM alerts, feedback emails, sends that are due, weather, and the morning job's first step) and starts workers; workers (`/api/jobs/work`, started every minute by Supabase when jobs are due, by the hourly job and by each WhatsApp message) take jobs a few at a time, each with its own time budget, so one slow or failing restaurant never delays another. Owner messages go on the queue too (answered first, one at a time per restaurant); if one fails the owner gets the usual "Sorry" once and the builder is alerted. The morning job is a chain of steps in the same order as before, the brief last. Retries wait 1, 5, 15 then 60 minutes; a job that uses its tries is dead and the builder is told (never the owner). Limits per job type (Claude, Resend) in the `job_types` table. The old agent queue runs on it (`agent_jobs` stays as the record of agent work). External workers (the coming Python service) use their own login and can only claim, finish or fail their own job types. Alerts for a backed-up queue, stuck jobs and any brief not out by 9:30 (a brief held for WhatsApp's 24-hour rule counts as ready). /log shows each restaurant's queue and dead jobs with a Retry button (in the audit log). Finished jobs are cleared after 14 days, dead ones after 90. A simulated Monday with 50 restaurants has every brief out by 9:13.

26. Analytics service (`analytics/service`, Python), the worker that will run the statistical models outside the app, proven end to end with one benchmark model. It logs in only as `queue_worker` (reads the `analytics` views, adds model outputs, finishes its own runs, uses the `ext_*` queue functions), takes its own job types from the queue, runs each job in its own process with a time budget and heartbeats, finishes or fails it through the queue (retries, backoff, dead-job alerts to the builder), and stops cleanly (the running job is given back without using a try). A model is one file plus one registration line (name, version, kind, role, job type, the views it reads, a run function); the runner creates the `model_runs` row, writes the outputs tied to it and finishes it. First model: `forecast_baseline`, same weekday averaged over the last 4 weeks, 14 days ahead, for orders (all and per channel), covers (all and per channel) and net sales (all), with low/likely/high from the spread. It is a **benchmark** (`model_runs.role`, migration 039): never shown to an owner, whatever its back-test says. Every forecast model scores itself with the same 12-week rolling back-test (issued at 05:35 UK each night, using only trading days that had ended by then); orders/all is the headline. The app queues one job per model per active restaurant, due at 05:35 UK (after the 05:00 trading-day cut-off, so yesterday counts; queued by the 05:05 hourly run, 09:00 backup), only while `ANALYTICS_JOBS=true`. Dev CLIs: enqueue, run-one, status, check. Hosting: Railway (approved; deployed once the real forecast model passes its back-test).
27. Demand forecast model (`forecast_daily`, role production; no AI, pure statistics), in `analytics/service/src/dinerai_analytics/models/forecast_daily/`. Per restaurant and channel, a negative binomial regression: level, trend, yearly season (Fourier), weekday, and channel-specific factors (bank holidays and the days around them, Christmas to New Year as four days, Mother's Day, Valentine's, school holidays and inset days by council, payday and the 2 days after, clock changes, Diwali, Ramadan in three phases, Eid al-Fitr and al-Adha days 1 to 3, chand raat, weather against its seasonal normal, rain at lunch and dinner, sunshine, heat, sport matches by importance and team relevance (football now; cricket ready for a fixtures feed), venue crowds fading with distance, disruption days, each deal, the menu price index), offset by real hours open. Fitted nightly on all history by penalised maximum likelihood with a Normal prior per weight from editable defaults per restaurant type (`defaults/general|halal|cafe|takeaway.json`, each with a reason) and 26-week time-decay weights. Ranges: simulated (parameter and count uncertainty), then calibrated on the back-test (split-conformal, last 8 weeks of errors, per series and horizon bucket). Hour profile per channel and day type (Ramadan aligned to maghrib, Friday Jummah to dhuhr), adding up exactly; channels add up to all. Sales (net) and covers derived from orders. 56 days daily, 14 days hourly. Uncertain moon-sighting dates are blended 50/50 (or by `alt_probability`). Choices made by back-test on a separate window every 28 days (season terms, weekday x summer, decay vs recent-level correction, sum of channels vs direct). Pass bar (written to `model_runs.passed`, the same for every restaurant): orders/all no worse than `forecast_baseline` on the 12-week back-test and at least 10% better on the long back-test (50 cut-offs across the history, so Ramadan and Eid count; made every 28 days and cached in the run's metrics); each channel with 15% of orders no more than 5% worse than the baseline on the 12 weeks; 80% coverage 75 to 88% and bias under 5% for all of them; 8 weeks of history. (The first bar, 15% better than the baseline on the 12 weeks with coverage 75 to 85%, was replaced on 18 Oct 2026 as a change of principle, with the model unchanged.) Outputs: `forecasts`, `model_coefficients`, `forecast_drivers` (migration 040). `forecast_refresh` at 07:00 UK re-predicts days 0 to 2 with the newest weather and calendar from the 05:35 run's weights. Results on dinerai-dev (issued 17 Oct 2026): all four demo restaurants pass the revised bar; under the first bar only Broadway Late Grill and Fern and Fold passed (Saffron Lane and its messy copy were 7% and 10% better than the baseline on the 12 weeks, 13.5% and 17% over the long back-test).

## Design rules to keep following
- Every message to the owner carries a decision or a result. No "just checking in".
- Do the work before asking: arrive with a finished draft so approval is one tap.
- Batch, don't drip. Real-time only for urgent things.
- Nothing reaches a customer unchecked.
- Every feature gets a test command so the owner can trigger it without waiting.

## Now protected
- Only a registered owner number can use WhatsApp, and only for its own restaurant; fake (unsigned or tampered) and duplicate messages are rejected; unknown numbers get one polite reply a day.
- One restaurant can never see or send to another's customers, drafts or reviews (isolation tests).
- Owner web pages need a login; report links expire after 30 days.
- Every send passes the four checks; consent and unsubscribe links are re-checked at send time.
- Every action is logged with who and when; UNDO reverses the owner's last action where possible.
- Scheduled jobs record real outcomes and alert the builder on failure, a stuck run or lateness; no review is skipped by a timeout.
- Test commands and the test clock are off unless TEST_TOOLS is on, and never act on a real (non-demo) restaurant; dummy data can be cleared in one go.
- Claude never receives the customer list or contact details.
- Allergens are never shown to customers, or used in messages to them, until the owner confirms them.
- Customer emails come from our authenticated domain (DKIM, SPF and DMARC pass); nobody gets marketing until they confirm their email; dummy addresses are never emailed; with EMAIL_REDIRECT on (always on in preview and development) nothing reaches real customers.
- The sign-up form has a CAPTCHA (when its keys are set), a bot trap and rate limits; feedback, confirm and delete endpoints are rate-limited.
- Every customer email has Unsubscribe and Delete my data links; the Google review link goes to every customer, never only happy ones.
- Deletions and customer-list exports are in the audit log; export links expire after an hour.
- A WhatsApp number is only linked to a restaurant by sending that restaurant's one-time code (from its logged-in setup page); guessing is capped per number.
- Tests run on every push and before every deploy.
- Billing: Stripe calls are server-side only and live keys are refused; webhook events must carry Stripe's signature and are handled once each; paying never logs anyone in (the login link goes to the restaurant's email); /start never attaches billing, invite codes or terms to a running restaurant; pilot codes can only be used through the database function, up to their limit.
- Staff numbers can only send till reports and sales files for their own restaurant (one restaurant per number); they can't chat, approve or change anything.
- Sales data follows the same isolation rules and tests as everything else; till report photos and POS files are in a private bucket (signed links that last an hour); the AI only sees a few POS rows to work out the columns, with staff, customer and contact details blanked out.
- The AI only reads till reports; plain code decides whether they add up, and nothing doubtful is saved without a YES.
- A question for the owner (about a review, or a bank holiday's hours) is never sent by the gate, and APPROVE ALL leaves it for the owner's own answer.
- Changes to hours or the menu on Google always need the owner's Approve (never Auto or Draft only). No agent goes live unless AGENTS_LIVE_ALLOWED allows it and its readiness check passes, and AGENTS_LIVE_ALLOWED=false puts every agent back in shadow at once. Visibility's staff tips are fixed wording. Reputation can only go live once its go-live checklist passes, and then the checker is blocking for its replies.
- Trust levels are per task and only the builder can change them; campaigns, offers, hours, menu and profile changes can never be Auto, and Auto needs a live checker pass on that exact version (enforced in code, not in a prompt).
- With GOOGLE_MODE=simulated (and always in preview and development) the gate itself stops anything reaching live Google; WhatsApp to customers is off until Meta verification.
- No customer gets more than one campaign in any 7 days (birthday emails excepted), checked in code at send time.
- Agents only get the tools listed in their file (an allow-list in code), never a tool that sends, publishes or spends, and only their own restaurant's data. An agent can't change a settings-only profile field (the cap, the send window).
- Scheduled work runs one job per restaurant per task on a queue: one slow or failing restaurant never delays another; two workers never run the same job; a job that keeps failing stops after its tries and the builder is told (never the owner); an owner whose message failed gets one "Sorry". The queue's functions can't be called with the public key, and the external worker login can only touch its own job types, never a table.
- The menu has one home (dishes): `restaurants.menu` is only a copy and the database refuses any other change to it (after 037). Prices, pay rates, costs and targets are never overwritten, and back-tests can only see what was known at the time.
- Every operations table has Row Level Security policies (an owner reaches only their restaurant's rows; history can't be changed through them). The Python service reads only the analytics views (no staff names, photos or contact details) and can only add model outputs and finish its own runs.
- Benchmark model runs (e.g. the baseline forecast) never reach an owner: the app only shows outputs of production runs that succeeded and passed, one file reads model outputs (enforced by a test), and the database hides benchmark runs and their outputs from owner logins. The analytics service refuses production unless told explicitly, never uses the Supabase secret key, and a job is never run by two workers or left locked.
- Owners only see forecasts from production runs that succeeded and passed, read through the one model-output file. The demo-only override needs TEST_TOOLS, a demo restaurant and its setting (the database refuses the setting on a real restaurant, and a test proves the override never applies to one); every such forecast is labelled "TEST: unvalidated forecast". Every forecast number an owner sees is made by code; an assistant answer that quotes any other number, or talks about staff, is replaced by code's lines.
- Staff data is minimal (no NI numbers, addresses, bank details or dates of birth); a person can be forgotten (details gone, wage records kept unnamed).

## Known limits (to fix before real restaurants)
- Restaurants are kept apart by the code (every query filtered, enforced by tests), not by the database: the app uses Supabase's secret key, which bypasses row-level security. Adding RLS policies per restaurant would be a second, database-level wall.
- Anyone can use the restaurant sign-up page (`/start`), behind Turnstile, a hidden bot field, rate limits and at most 5 unfinished sign-ups per email per day. A new restaurant stays inactive until onboarding finishes. All restaurants share the Twilio sandbox number, and each owner must join the sandbox first.
- Onboarding's Google step needs GOOGLE_PLACES_API_KEY; without it the step is skipped. Menu reading and allergen suggestions are Claude's best guess: the owner checks them, and allergens are never used for customers until confirmed.
- WhatsApp sandbox: outside the 24-hour window the 9am brief waits for the owner's next message, and builder WhatsApp alerts may not arrive (needs a Meta-approved template and a real sender). Email alerts still work.
- Email: Supabase's built-in login email is rate-limited (a few per hour). Customer emails land in Gmail's Promotions tab (normal for offers). Resend's free plan: 100 emails a day, 3,000 a month. The fixed email wording comes in three tones picked from the brand voice by keywords, not written per restaurant. Preview pictures are a close drawing of the email, not a screenshot. A customer who never ticked the marketing box still gets the "How was your visit?" email (a service message, no offers) unless they unsubscribe.
- The compliance check for misleading claims is a word list: it catches common problems, not every one.
- UNDO can't take back an email already sent, or changed hours on live Google (live replies and posts are deleted).
- Tests replace the database with a stand-in; nothing yet runs against a real test database.
- Live Google: the OAuth app is unverified until Google reviews it (owners see "Google hasn't verified this app" and click Advanced; up to 100 users). Posts are all "What's new" posts (offers and events need dates Google insists on). The menu isn't sent to Google. RUN REVIEWS only works on demo restaurants (test tools), so a real restaurant's new reviews arrive with the hourly check.
- Billing (step 22): Stripe test mode only. The landing page's company name, number and registered office are placeholders. Cancelling at period end and trial-ending reminder emails are Stripe dashboard settings, not code. A preview's webhook needs Vercel's protection bypass (or the Stripe CLI locally). If the webhook is late or missing, a paid restaurant finishes onboarding inactive until the subscription event arrives. A restaurant the builder switched off by hand is switched back on by its next Stripe event if it's paying. All new trial owners still need to join the Twilio sandbox. Still to test live on the preview (done so far: paid sign-up with 4242, login link, setup, cancel at period end): a failed payment (card 4000 0000 0000 0341, then a £1 one-off invoice in Stripe charged automatically, to fire invoice.payment_failed: check the log line and the builder alert; ending the trial from the dashboard doesn't work with that card, Stripe refuses the change), and a pilot invite code (a row in pilot_invites, then /start?invite=CODE: no card asked, login link). Preview sign-ups linking WhatsApp go through the live webhook, which in test mode moves the phone off Ember & Spice: don't link WhatsApp on billing test restaurants.
- Sales: till report reading is Claude's reading of a photo (checked by code, but a misread figure that still adds up would be saved). POS files: CSV and .xlsx only (not old .xls); net is estimated at 20% VAT (food at other rates would be slightly off); sales are only counted when the file has a receipt/order number column. File layouts are learned per restaurant. Twilio's WhatsApp may not deliver every document type (CSV from some phones); the web upload always works. Weather is Open-Meteo's model data for the restaurant's postcode (via postcodes.io), not a weather station. The brief only nudges restaurants that have sent a till report in the last 14 days.
- Agents (phases 1 and 2): the checker is only blocking for Reputation's own replies (live mode); everywhere else it records in shadow mode. The old single assistant still writes every draft except review replies at restaurants where Reputation is live. Weekly themes are checked by code (the reviews exist, counts), not by the checker. The checker's verdicts aren't fully steady run to run (Sonnet 5.5 doesn't take temperature 0); the stability runs measure it. A question card's answer can't be undone with UNDO. Drafts from before the agents have no sources of their own, so code lists the profile fields each kind may rely on. Rendered previews exist for emails only (B1 to B4 are skipped for posts and replies). Only the profile fields Reputation, Visibility and the checker need are stored so far. Visibility (phase 3a): Google isn't connected for hours, menus or posts (dummy mode logs what would have been sent); live mode needs AGENTS_LIVE_ALLOWED=true (or the deprecated TEST_MODE); trend ideas and local calendar dates (religious dates, local events) wait for a trend scan and a local calendar; special hours can only be set by answering the bank holiday question (no settings field yet); a hours update can still be "edited" as text, which doesn't change the hours themselves.
- Insights (phase 3b): unless the GM is live, number questions are spotted by a word list, so some are missed and a few others are sent to it (shadow only costs money). Live mode needs AGENTS_LIVE_ALLOWED=true (or the deprecated TEST_MODE). Covers aren't recorded (transactions instead); dish margins, labour cost and sales targets need data no restaurant has yet (menu engineering and rival watch are later). Google views, calls and direction requests don't exist until Google is connected. "Last week" is always the last full Monday to Sunday, so RUN REPORT mid-week covers a different week from today's report. When a week's figures are incomplete, Insights asks for the missing till reports rather than writing the report words (live: today's words are kept; the question goes in the brief when the GM is live, otherwise it's only recorded). Answers take 10 to 40 seconds (tool calls plus the checker); the "On it" line covers the wait only when the GM is live.
- Switches (step 22) are Vercel environment variables: a change only takes effect after a redeploy (Vercel, Deployments, the latest one, Redeploy; about two minutes), so the kill switch is fast but not instant. Changing them in Vercel isn't in the restaurant's audit log; the next cron run records them and /log marks the change. Per-restaurant control is the builder's agent mode in settings; the switches are the same for every restaurant.
- Growth (phase 3c): live mode needs AGENTS_LIVE_ALLOWED=true (or the deprecated TEST_MODE). A scheduled campaign goes out at the first hourly run after its send time (up to an hour late). Questions from the live Monday work, and special ideas, reach the owner only through the GM's brief (when the GM is live); otherwise they're recorded, and special ideas stay on /log.
- The GM (phase 4): live mode needs AGENTS_LIVE_ALLOWED=true (or the deprecated TEST_MODE). General chat, look-ups, pasted reviews and drafts for a specialist in shadow still go to today's single assistant (its big prompt is retired only once the builder confirms). If the router is slow (over 10 seconds) or fails, today's assistant answers. Button titles set per message (the "which did you mean?" choices) haven't been tried on the real Twilio sandbox yet; typing 1, 2 or 3 always works. Allergen and halal statements can't be changed by message (settings page only). Alerts are held at most until the next hourly job, so a held alert can arrive up to an hour after it's due. Replies to simple profile questions go through the checker, which adds a few seconds. The calendar has bank holidays only until the builder adds religious dates, school holidays and local events. Free-item offers are measured against one dish's price, so "free dessert with any main" counts against the cheapest main; owners who want generous free items can raise their cap. Growth asks when details are missing (uncertain dates, reward terms, hours that don't fit), which is right but means fewer drafts until the profile is fuller.
- Job queue (step 23): an owner's reply waits for a worker to start (about half a second; if the kick fails, up to a minute for Supabase's schedule). Owner messages get one try only (a retry could answer twice). Claims are one at a time across the whole queue (a short lock, milliseconds each), fine for hundreds of restaurants, not for many thousands of jobs a minute. Limits are per job type, not one shared Claude limit: about 30 jobs can run at once with today's numbers (the simulation's peak was 33 with owner messages). Local servers share the queue with the live site: a local message is normally answered by the local server (its kick is instant), but the live site's every-minute workers can take queued work too. The Monday post step runs Visibility's job straight away only if an agent slot is free (6 at once); otherwise the post arrives after the brief. PGlite can't test truly simultaneous claims (`scripts/queue-race.mjs` does, on the real database). The simulation's timings use stand-in durations for Claude (10 to 60 seconds) and email, not measured ones.
- Operations data (step 24) is schema only: nothing fills staff, rotas, invoices, recipes, covers or channels yet (the calendar, weather and prayer times are filled by the outside data feeds since step 28, model outputs by the analytics service), and no screen or WhatsApp flow uses them. Menu readers still read the `restaurants.menu` copy (identical to before); a future-dated price change shows in the copy at once. Dishes are matched by name when a menu arrives without ids (onboarding, UNDO, Revert): two dishes with the same name in one restaurant are told apart by position only. The app still bypasses RLS (secret key); the new policies only protect logins that don't. Staff retention (6 years for hours and pay, 3 months for availability) is a proposal to check with an accountant, and `apply_staff_retention` isn't scheduled yet. Weather forecasts as issued: from the feeds (step 28) `issued_at` is when we fetched it and `model_run_at` the weather model's own run; archived ones (backfill) only go back to early 2024. Supabase's login roles: `queue_worker` still has no password until the Python service exists.
- Analytics service (step 26): not deployed yet (Railway approved; the builder deploys it once the real forecast model passes its back-test, and ANALYTICS_JOBS stays off until then). Since step 31 the brief, the assistant and the Monday report show forecasts from passed runs (see step 31). The nightly run is at 05:35 UK so yesterday counts; a restaurant whose trading-day cut-off is after 05:35 gets data up to the day before yesterday. `finish_model_run` lets queue_worker finish any running run, not only its own. Sales per channel include VAT while daily sales are net, so channel sales aren't forecast. Covers forecasts are weak for small groups (the late takeaway's dine-in).
- Demand forecast (step 27): only tested on synthetic data. On it, the halal datasets (Saffron Lane, its messy copy) are only about 7% and 10% better than the baseline on the 12-week back-test (13.5% and 17% over the long back-test): they pass the revised bar but not the first one; Saffron Lane's takeaway is 2.5% worse than the baseline on the 12 weeks (allowed up to 5%) and the messy copy's coverage is 86.6% (allowed up to 88%). Much of what's left is day-to-day noise the generator adds. The builder had read the generator's README (which lists its true effects) before the defaults were written down; the defaults were approved beforehand and not changed. Days 7 onwards use normal weather, so a sun-driven cafe loses most of its weather edge there. Effects that happened once or twice in two years (New Year's Eve, one Eid al-Adha) stay near their defaults; recovery got about three quarters of comparable effects within tolerance. Seat capacity isn't recorded, so censoring is coded but off. Deals count from when they were sent, so a deal starting the day after it goes out is missing from that night's forecast. The 07:00 refresh keeps each range's width relative to its likely value, so a confirmed moon sighting moves the forecast but doesn't narrow the range; sales follow orders/all's change, not each channel's. A nightly run takes 35 to 60 seconds per restaurant on the builder's laptop, and 65 to 95 seconds on the night every 28 days that re-makes the long back-test (Railway's CPU may be slower; the budget is 10 minutes, and the job's 300 s lock is extended by the heartbeat). The calendar has no recorded-at time, so back-tests see calendar rows (and closures) as known in advance.
- Outside data (step 28): see `docs/before-launch.md`. Open-Meteo's free tier is non-commercial; Ticketmaster's and football-data.org's commercial terms are unconfirmed. Cricket, England's non-tournament matches, National Rail strikes and inset days are builder entry. Ticketmaster has no past events and TfL no past disruption, so the history has none from them. Archived forecasts start in early 2024. A restaurant's old weather forecasts stay as issued when it moves (they can't be changed). The calendar view's rule is in SQL and in `lib/feeds/scope.ts` (a test checks they agree). Owner-reported events go through today's assistant only, not the GM's router: with the GM live, "there's a fair on Saturday" may be routed as a fact about the restaurant instead.
- Rota suggester (step 34): greedy, not optimised: it can use someone's day on a short peak shift and leave a quieter day open, and long days get two overlapping shifts (so some hours have more people than the rules need). No breaks (pay is hours x rate; unpaid breaks aren't taken off), no holiday pay or employer costs in the labour %. Shift times are exactly the opening hours (no prep or close-down time). A shift needs someone's availability to cover all of it, or at least the minimum length from the first short half hour. Approved time off in `staff_time_off` is honoured, but nothing fills that table yet (a rota edit like "Ali can't do Friday" does the job for one week). Edits are kept for that week only; changing a time ("Ali finishes at 6") isn't an edit it understands. Staff names are matched by first name, so two people with the same first name need their full names. The Thursday draft is a plain WhatsApp message, so outside the 24-hour window it doesn't arrive (text ROTA to bring it up). A rebuild (RUN ROTA) or an edit replaces all of the week's shifts.
- Forecast for owners (step 31): only seen on demo restaurants with the TEST override so far (no restaurant's production run has passed on real data). Forecast questions go to today's assistant, not the GM's router or Insights. A normal day is worked out from orders only (a restaurant with sales but no order counts gets no days-ahead flags). The "Yesterday" line needs yesterday's brief to have shown a forecast. Channel lines show orders only (channel sales aren't forecast). The quiet-night offer checks the 7-day gap for the day before the quiet day at 10:00; the campaign's own checks still run when it's drafted and sent. The offer buttons are a new Twilio template, made automatically the first time.
